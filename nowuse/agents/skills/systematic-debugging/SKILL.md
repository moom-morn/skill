# 系统性调试

## 概述

随机修复浪费时间并制造新 bug。快速补丁掩盖潜在问题。

**核心原则：** 在尝试修复之前，总是先找到根因。治标不治本等于失败。

**违反此流程的文字即违反调试的精神。**

## 铁律

```
没有先调查根因，就没有修复
```

如果你没有完成第一阶段，就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**尤其要使用**当：
- 时间紧迫（紧急情况让你想猜）
- "快速修一下"似乎很明显
- 你已经尝试过多次修复
- 之前的修复没起作用
- 你没有完全理解问题

**不要跳过**当：
- 问题看似简单（简单 bug 也有根因）
- 你很赶时间（匆忙保证返工）
- 经理要马上修好（系统性的比乱撞快）

## 四个阶段

你必须在进入下一阶段之前完成每个阶段。

### 第一阶段：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 每次都会发生吗？
   - 如果不可复现 → 收集更多数据，不要猜测

3. **检查最近的改动**
   - 什么改动可能导致这个问题？
   - Git diff、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名、API → 服务 → 数据库）：**

   **在提出修复之前，添加诊断工具：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传递
     - 检查每层的状态

   运行一次以收集证据，显示哪里出问题
   然后分析证据，识别失败组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：密钥链状态
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓, workflow → build ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   完整的回溯追踪技术见本目录的 `root-cause-tracing.md`。

   **简易版：**
   - 错误值从哪里起源？
   - 谁用错误值调用了这里？
   - 持续向上追踪直到找到源头
   - 在源头修复，不在症状处修复

### 第二阶段：模式分析

**在修复之前找到模式：**

1. **找到工作示例**
   - 在同一代码库中找到相似的工作代码
   - 什么工作代码与被破坏代码相似？

2. **对比参考**
   - 如果是在实现某个模式，完整阅读参考实现
   - 不要浏览——逐行阅读
   - 在应用之前完全理解模式

3. **识别差异**
   - 工作代码和被破坏代码之间有什么不同？
   - 列出每一个差异，不管多小
   - 不要假设"那肯定不重要"

4. **理解依赖**
   - 这需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了什么假设？

### 第三阶段：假设与验证

**科学方法：**

1. **形成单一假设**
   - 明确陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 具体，不要模糊

2. **最小验证**
   - 做**最小**的改动来验证假设
   - 一次只变一个变量
   - 不要同时修复多个问题

3. **验证后再继续**
   - 有效？→ 第四阶段
   - 无效？形成**新**假设
   - **不要在上面叠加更多修复**

4. **当你不确定时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 进一步研究

### 第四阶段：实现

**修复根因，不是症状：**

1. **创建失败测试用例**
   - 最简单的复现方式
   - 如果可能，做成自动化测试
   - 如果没有测试框架，写一次性测试脚本
   - 在修复之前必须有
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 针对已识别的根因
   - **一次**只改一处
   - 不要"顺手"改进
   - 不要附带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏？
   - 问题真的解决了吗？

4. **如果修复无效**
   - 停下来
   - 计数：你已经尝试了多少次修复？
   - 如果 < 3：回到第一阶段，用新信息重新分析
   - **如果 ≥ 3：停下来质疑架构（下面的第 5 步）**
   - **不要**在未讨论架构的情况下尝试第 4 次修复

5. **如果 3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复在不同的地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复在其他地方制造新症状

   **停下来质疑基本问题：**
   - 这个模式从根本上合理吗？
   - 我们是否"因为惯性而坚持"？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的用户伙伴讨论**

   这不是假设失败——这是架构错误。

## 红灯信号 - 停下来遵循流程

如果你发现自己这样想：
- "先快速修一下，之后再调查"
- "试试改 X 看看行不行"
- "同时改多个地方，跑测试"
- "跳过测试，我手动验证"
- "可能是 X，让我修一下"
- "我没有完全理解但这可能行"
- "模式是 X 但我改改方式"
- "主要问题是：[列出修复项但没有调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（当已经尝试 2+ 次时）**
- **每次修复在不同地方揭示新问题**

**所有这些意味着：停下来。回到第一阶段。**

**如果 3+ 次修复失败：** 质疑架构（见第四阶段第 5 步）

## 你的用户伙伴的信号表明你做错了

**注意这些重定向：**
- "那不是没发生吗？" — 你没有验证就假设了
- "它能否给我们展示……？" — 你本应添加证据收集
- "别猜了" — 你在不理解的情况下提出修复
- "深入思考一下" — 质疑基本问题，不只是症状
- "卡住了？"（沮丧）— 你的方法不起效

**当你看到这些时：** 停下来。回到第一阶段。

## 常见狡辩

| 借口 | 真相 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 bug 也很快。 |
| "紧急情况，没时间走流程" | 系统性调试**更快**，比猜了改、改了猜快。 |
| "先试试这个，再调查" | 第一次修复就定下基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复不牢固。先测试证明它。 |
| "同时修复多个省时间" | 无法隔离哪个有效。制造新 bug。 |
| "参考太长了，我适配一下模式" | 部分理解保证有 bug。完整阅读。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|----------|
| **1. 根因** | 阅读错误、复现、检查改动、收集证据 | 理解**什么**和**为什么** |
| **2. 模式** | 找到工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小验证 | 已确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决、测试通过 |

## 当流程揭示"没有根因"

如果系统性调查发现问题是环境、时序或外部因素造成的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志以便将来调查

**但是：** 95% 的"没有根因"案例是调查不完整。

## 辅助技术

这些技术是系统性调试的一部分，位于本目录中：

- **`root-cause-tracing.md`** — 通过调用栈向后追踪 bug，找到原始触发点
- **`defense-in-depth.md`** — 找到根因后在多层添加验证
- **`condition-based-waiting.md`** — 用条件轮询替换任意超时

**相关技能：**
- **superpowers:test-driven-development** — 用于创建失败测试用例（第四阶段第 1 步）
- **superpowers:verification-before-completion** — 在声称成功之前验证修复有效

## 真实影响

来自调试会话的实际数据：
- 系统性方法：15-30 分钟修复
- 随机修复方法：2-3 小时乱撞
- 首次修复成功率：95% vs 40%
- 引入新 bug：近乎零 vs 常见
