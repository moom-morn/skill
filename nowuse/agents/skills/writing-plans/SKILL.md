# 编写计划

## 概述

编写全面的实现计划，假设工程师对我们的代码库零上下文且品位可疑。记录他们需要知道的一切：每个任务要触碰哪些文件、代码、测试、可能需要查看的文档、如何测试。给他们完整的、颗粒度的任务计划。DRY。YAGNI。TDD。频繁提交。

假设他们是熟练的开发者，但几乎不了解我们的工具集或问题领域。假设他们不太擅长好的测试设计。

**开始时声明：** "我将使用 writing-plans 技能来创建实现计划。"

**上下文：** 如果在隔离的 worktree 中工作，它应在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**计划保存到：** `agents/plans/superpowers/YYYY-MM-DD-<feature-name>.md`

-   （用户对计划位置的偏好覆盖此默认值）

## 范围检查

如果规格涵盖多个独立的子系统，在脑暴阶段就应该已被拆分为子项目规格。如果当时没有拆分，建议将其拆分为多个计划——每个子系统一个。每个计划本身应产生可工作的、可测试的软件。

## 文件结构

在定义任务之前，先规划哪些文件将被创建或修改，以及每个文件的职责。这是分解决策落定的地方。

-   设计边界清晰、接口定义良好的单元。每个文件应有一个明确的职责。
-   你能推理最好的是能同时放在上下文中的代码，文件聚焦时你的编辑也更可靠。优先选择更小、更聚焦的文件，而不是塞得过多的大文件。
-   一起变更的文件应该放在一起。按职责拆分，而不是按技术层。
-   在现有代码库中遵循已有模式。如果代码库使用大文件，不要单方面重构——但如果你正在修改的文件已经变得笨重，在计划中包含拆分是合理的。

这个结构指导任务分解。每个任务应产生自包含的、独立合理的改动。

## 颗粒度的任务

**每个步骤是一个动作（2-5 分钟）：**

-   "编写失败的测试" — 一步
-   "运行确认它失败" — 一步
-   "实现最小代码使测试通过" — 一步
-   "运行测试确认通过" — 一步
-   "提交" — 一步

## 计划文档头

**每个计划必须以以下头部开始：**

```markdown
# [功能名称] 实现计划

> **供代理工作者使用：** 必需的子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 来逐个任务实现此计划。步骤使用 checkbox（`- [ ]`）语法追踪。

**目标：** [一句话描述要构建什么]

**架构：** [2-3 句话描述方案]

**技术栈：** [关键技术/库]

---
```

## 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**

-   创建：`exact/path/to/file.py`
-   修改：`exact/path/to/existing.py:123-145`
-   测试：`tests/exact/path/to/test.py`

-   [ ] **第 1 步：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

-   [ ] **第 2 步：运行测试确认失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL 返回"function not defined"

-   [ ] **第 3 步：编写最小实现**

```python
def function(input):
    return expected
```

-   [ ] **第 4 步：运行测试确认通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

-   [ ] **第 5 步：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 无占位符

每个步骤必须包含工程师需要的实际内容。以下是**计划失败**的标志——永远不要这样写：

-   "TBD"、"TODO"、"稍后实现"、"补充细节"
-   "添加适当的错误处理" / "添加验证" / "处理边界情况"
-   "为以上内容编写测试"（没有实际测试代码）
-   "类似于任务 N"（重复代码——工程师可能按乱序阅读任务）
-   仅描述做什么但不展示如何做的步骤（代码步骤必须要有代码块）
-   引用任何任务中未定义的类型、函数或方法

## 牢记

-   总是用精确的文件路径
-   每个步骤中完整的代码——如果一个步骤修改代码，展示代码
-   精确的命令及预期输出
-   DRY、YAGNI、TDD、频繁提交

## 自查

编写完整计划后，用全新眼光审视规格，对照检查计划。这是你自行运行的检查清单——不是派生子代理。

**1. 规格覆盖：** 浏览规格中的每个章节/需求。能否指向一个实现它的任务？列出任何差距。

**2. 占位符扫描：** 搜索计划中的红旗信号——上面"无占位符"部分中的任何模式。修复它们。

**3. 类型一致性：** 后面任务中使用的方法签名和属性名是否与你之前任务中定义的匹配？任务 3 中叫 `clearLayers()`，任务 7 中叫 `clearFullLayers()` 就是 bug。

如果发现问题，内联修复。不需要重新审阅——修复即可继续。如果发现规格需求没有对应任务，添加任务。

## 执行交接

保存计划后，提供执行选择：

**"计划完成并保存到 `docs/superpowers/plans/<filename>.md`。两种执行方式：**

**1. 子代理驱动（推荐）** - 我每个任务派发一个全新子代理，任务间审阅，快速迭代

**2. 内联执行** - 在此会话中使用 executing-plans 执行，批量执行带检查点

**选哪种？"**

**如果选择了子代理驱动：**

-   **必需的子技能：** 使用 superpowers:subagent-driven-development
-   每个任务全新子代理 + 两阶段审阅

**如果选择了内联执行：**

-   **必需的子技能：** 使用 superpowers:executing-plans
-   批量执行带检查点用于审阅
