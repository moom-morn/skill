# 完成前验证

## 概述

声称工作已完成而不验证是欺骗，而不是高效。

**核心原则：** 证据先于声明，永远如此。

**违反此规则的文字即违反其精神。**

## 铁律

```
未经新的验证证据，不得声称完成
```

如果你没有在本条消息中运行过验证命令，就不能声称它通过了。

## 关卡函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能验证这个声称？
2. 运行：执行完整命令（新的、完整的）
3. 阅读：完整输出，检查退出码，统计失败数
4. 验证：输出是否确认了声称？
   - 如果不是：陈述实际状态并附上证据
   - 如果是：附上证据陈述声称
5. 然后：才能做出声称

跳过任何步骤 = 说谎，而不是验证
```

## 常见失败

| 声称 | 需要 | 不足够 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 failures | 之前的运行、"应该能过" |
| Lint 干净 | Linter 输出：0 errors | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Lint 通过、日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了、假设好了 |
| 回归测试有效 | 红绿循环已验证 | 测试通过一次 |
| 代理已完成 | VCS diff 显示改动 | 代理报告"成功" |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 红灯信号 - 停下来

- 使用"应该"、"可能"、"看起来"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成了！"等）
- 即将在未验证的情况下提交/push/PR
- 相信代理的成功报告
- 依赖部分验证
- 想"就这一次"
- 累了想结束工作
- **任何在没有运行验证的情况下暗示成功的措辞**

## 预防狡辩

| 借口 | 真相 |
|------|------|
| "现在应该可以了" | 运行验证 |
| "我很确信" | 自信 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Lint 过了" | Lint ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "我累了" | 累不是借口 |
| "部分检查就够了" | 部分证明不了什么 |
| "措辞不同所以规则不适用" | 精神大于文字 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 pass] "所有测试通过"
❌ "现在应该能过" / "看起来正确"
```

**回归测试（TDD 红绿）：**
```
✅ 编写 → 运行（通过） → 撤销修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ "我已经写了回归测试"（没有红绿验证）
```

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Lint 过了"（Lint 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建检查清单 → 逐项验证 → 报告差距或完成
❌ "测试通过，阶段完成"
```

**代理委托：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证改动 → 报告实际状态
❌ 相信代理报告
```

## 为什么这很重要

来自 24 次失败记忆：
- 你的用户伙伴说"我不相信你" — 信任破裂
- 未定义的函数发布出去 — 会崩溃
- 缺失的需求发布出去 — 功能不完整
- 时间浪费在虚假完成 → 重定向 → 返工
- 违反了："诚实是核心价值。如果你撒谎，你将被替换。"

## 何时应用

**在所有以下情况之前：**
- 任何形式的成功/完成声明
- 任何满意表达
- 关于工作状态的任何正面陈述
- 提交、创建 PR、任务完成
- 移动到下一个任务
- 委托给代理

**规则适用于：**
- 准确的措辞
- 同义转述和同义词
- 暗示成功
- 任何沟通中暗示完成/正确

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后声称结果。

这是不可协商的。
