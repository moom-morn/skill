# 接收代码审查

## 概述

代码审查需要技术评估，而不是情感表演。

**核心原则：** 实施之前先验证。假设之前先提问。技术正确性优先于社交舒适。

## 回应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要立即反应
2. 理解：用自己的话重述要求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对这个代码库来说技术上合理吗？
5. 回应：技术确认或有理由的反对
6. 实施：一次一项，逐项测试
```

## 禁止的回应

**永远不要：**
- "你说得太对了！"（明确违反 CLAUDE.md）
- "好想法！" / "好反馈！"（表演性）
- "我现在就实现"（在验证之前）

**应该这样做：**
- 重述技术要求
- 问澄清问题
- 如果是错的，用技术理由反对
- 直接开始工作（行动 > 言语）

## 处理不清晰的反馈

```
如果有任何一项不清楚：
  停下来——什么都不要实施
  就不清楚的项目提问澄清

原因：项目可能互相关联。部分理解 = 错误实施。
```

**示例：**
```
你的用户伙伴："修复 1-6 项"
你理解了 1、2、3、6。4 和 5 不清楚。

❌ 错误：现在实施 1、2、3、6，稍后再问 4、5
✅ 正确："我理解 1、2、3、6 项。4 和 5 需要澄清后才能继续。"
```

## 按来源处理

### 来自你的用户伙伴
- **可信的** — 理解后实施
- **仍要问** 如果范围不清楚
- **不要表演性同意**
- **直接行动**或技术确认

### 来自外部审阅者
```
实施之前：
  1. 检查：对这个代码库来说技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上工作吗？
  5. 检查：审阅者理解了完整上下文吗？

如果建议看起来错误：
  用技术理由反对

如果无法轻松验证：
  说出来："没有 [X] 我无法验证。我应该 [调查/询问/继续] 吗？"

如果与你用户伙伴之前的决策冲突：
  先停下来与你的用户伙伴讨论
```

**你的用户伙伴的规则：** "外部反馈——要有怀疑精神，但要仔细核实"

## YAGNI 检查"专业"功能

```
如果审阅者建议"正确实现"：
  在代码库中 grep 实际使用情况

  如果没用到："这个端点没有被调用。要移除它吗（YAGNI）？"
  如果用到了：然后正确实现
```

**你的用户伙伴的规则：** "你和审阅者都向我报告。如果我们不需要这个功能，就别加。"

## 实施顺序

```
对于多条反馈：
  1. 先澄清任何不清楚的项
  2. 然后按此顺序实施：
     - 阻塞性问题（破坏功能、安全）
     - 简单修复（错别字、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试每个修复
  4. 验证无回归
```

## 何时反对

以下情况应该反对：
- 建议破坏现有功能
- 审阅者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈来说技术不正确
- 存在遗留/兼容性原因
- 与你用户伙伴的架构决策冲突

**如何反对：**
- 使用技术推理，不是防御性态度
- 问具体问题
- 引用工作测试/代码
- 如果涉及架构问题，让用户伙伴参与

**如果在公开表达反对时感到不自在：** "Strange things are afoot at the Circle K"

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述改动内容]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修复它，在代码中展示]

❌ "你说得太对了！"
❌ "好想法！"
❌ "谢谢发现！"
❌ "谢谢[任何事]"
❌ 任何感谢表达
```

**为什么不要感谢：** 行动胜于言语。直接修复它。代码本身表明你听到了反馈。

**如果你发现自己要写"谢谢"：** 删除它。陈述修复内容。

## 优雅地纠正你的反对

如果你反对了但是错的：
```
✅ "你是对的——我检查了 [X]，它确实 [Y]。正在实现。"
✅ "已验证，你是正确的。我最初的理解错了因为 [原因]。正在修复。"

❌ 长的道歉
❌ 为自己反对辩护
❌ 过度解释
```

真实地陈述纠正并继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量不测试 | 一次一项，逐项测试 |
| 假设审阅者永远正确 | 检查是否破坏东西 |
| 回避反对 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项 |
| 无法验证但仍继续 | 说明局限，请求方向 |

## 真实示例

**表演性同意（差）：**
```
审阅者："删除遗留代码"
❌ "你说得太对了！让我删掉……"
```

**技术验证（好）：**
```
审阅者："删除遗留代码"
✅ "检查中……构建目标 10.15+，这个 API 需要 13+。为了向后兼容需要遗留代码。当前实现的 bundle ID 错了——修复它还是放弃支持 13 之前的版本？"
```

**YAGNI（好）：**
```
审阅者："实现完整的指标追踪，包含数据库、日期过滤器、CSV 导出"
✅ "已 grep 代码库——没有任何地方调用这个端点。移除它（YAGNI）？还是我漏了用法？"
```

**不清楚的项（好）：**
```
你的用户伙伴："修复第 1-6 项"
你理解了 1、2、3、6。4 和 5 不清楚。
✅ "理解 1、2、3、6。4 和 5 需要澄清后再实施。"
```

## GitHub 线程回复

在回复 GitHub 内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶层 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，不是需要服从的命令。**

验证。质疑。然后实施。

没有表演性同意。始终技术严谨。
