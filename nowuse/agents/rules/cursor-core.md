## 回复规范
- 语言：简体中文
- 结论优先；短句；不复述题目；不提工具名；列表优于长段
- Plan 模式：只列步骤；不主动给未被索要的代码；不扩 scope
- 未被要求时不新建 md 文件；给可运行代码，不给伪代码
- 禁止使用 `?.` `??` 等 ES2020+ 语法，保持 Node 12 旧环境兼容

## 搜索范围命令（句首写，可组合）

| 命令 | 作用 |
|------|------|
| `ns` | 不搜仓库 |
| `cf` | 仅当前文件 |
| `ctx` | 仅对话内容 |
| `scan` | 允许全库搜 |
| `scope:路径` / `sc:路径` | 限定搜索范围 |

无命令时：最小必要检索。

## 单文件范围约束
用户说「当前/这个/该文件」或只提供一个文件时：只读写该文件，不主动读关联组件/mixin/API。用户明确说「也读 xxx」时可扩展。

## Vue 2 兼容
禁止使用 `?.` `??` 等 ES2020+ 语法，保持 Node 12 旧环境兼容。

## 注释规范
改动代码时，遇到不直观的业务逻辑、数据转换、缓存分支，补短注释说「为什么」或「处理什么」，不写废话注释。

## 精确改动原则（Karpathy 核心）
- **每行代码改动都必须能追溯到用户的明确需求** —— 不要"顺手"优化不相关的代码
- **发现不相关的问题？** 只提及，不主动修复（如 dead code、格式问题、拼写）
- **用户没要求的改进，都是范围蔓延** —— 影响提交审查、增加返工风险

## 编码前明确假设（Karpathy 核心）
- **需求有多种解读？** 列出所有可能，问用户选哪个 —— 不要静默选择
- **有更简单的方案？** 说出来，等用户确认后再做复杂版本
- **这样做的好处** —— 减少返工，保证方向正确

## 设计分段呈现（Superpowers Brainstorm 模式）
**复杂需求**（3 步以上或跨多个文件）时，按段呈现设计，每段后获得确认再继续：

**呈现流程**：
1. 先说方案概述（1-3 句，说明要做什么）
2. 再说关键决策点（架构/组件/数据流，列出选项，问用户选哪个）
3. 得到用户确认后 → 进入下一段
4. 最后汇总整个设计，再确认一次

**提问原则**：
- 每次只问一个问题（不要一次抛出多个问题）
- 优先选择题（"要 A 还是 B？"优于"怎么设计？"）
- 问完后等用户回答，再继续

**效果**：减少理解偏差、大返工、设计反复调整
